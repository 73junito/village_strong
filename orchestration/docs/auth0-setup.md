# Auth0 setup for release approvals

> **Status: design agreed, tenant not yet created.** No value below is real.
> `OIDC_CLIENT_SECRET` and the tenant domain must come from the Auth0 dashboard
> and must never be committed. Until the callback integration lands in a separate
> PR, none of this is wired into a live authorization flow.

Auth0 is the selected provider: standards-based Authorization Code + PKCE, a
per-user immutable `sub`, assignable roles, and RS256/JWKS signing that the
existing `jose` layer verifies without provider-specific code.

## Configuration

| Setting | Value |
|---|---|
| Application type | Regular Web Application |
| Flow | Authorization Code + PKCE |
| Signing algorithm | **RS256 only** |
| `OIDC_ISSUER` | `https://<tenant>.us.auth0.com/` |
| `OIDC_AUDIENCE` | The Auth0 application Client ID (validates the ID token `aud`) |
| `OIDC_JWKS_URL` | `https://<tenant>.us.auth0.com/.well-known/jwks.json` |
| `OIDC_ROLE_CLAIM` | `https://villagestrongfoundation.org/roles` |
| `OIDC_APPROVER_ROLES` | `release_approver` |
| `OIDC_CLIENT_ID` | Generated by Auth0 |
| Client authentication | Client secret, stored **only** as a Cloudflare secret |

The trailing slash on `OIDC_ISSUER` matters: `iss` is compared as an exact
string, so a missing or extra slash silently fails every token.

The role claim is a namespaced URI. `src/oidc.ts` reads it as a plain claim
lookup (`payload[roleClaim]`), so a namespaced claim needs no special handling —
and because the whole ID token is signature-verified first, a caller cannot
inject a role of their own.

## Approved staging design

| Setting | Value |
|---|---|
| Worker | `village-strong-orchestrator-staging` |
| Exposure | **`workers.dev` staging hostname only** |
| Custom domains / routes | **None** |
| Callback | `https://village-strong-orchestrator-staging.<workers-dev-subdomain>.workers.dev/oidc/callback` |
| Production Worker | Must remain nonexistent |
| Production zone / DNS | **Untouched** |

### Why `workers.dev` rather than a private binding

A service binding alone **cannot** receive a browser redirect. The OIDC callback
is a navigation the browser makes to the authorization server and back, so it
needs an address a browser can reach. A binding is addressable only from another
Worker on the same account — no browser can be pointed at one.

`workers.dev` satisfies that while keeping staging off production:

- the hostname sits under Cloudflare's `workers.dev` domain, **not** the
  `villagestrongfoundation.org` zone, so no production DNS record is touched and a
  routing mistake cannot reach the live site;
- no custom domain and no route are configured, so nothing appears in the
  production zone;
- it is a **separate Worker** (`...-staging`) with its own Durable Object
  namespace, secrets and data.

A separate zone (e.g. `villagestrong-staging.org`) stays a reasonable **future
fallback** if the `workers.dev` hostname is ever unsuitable. It is not needed now
and should not be created yet.

### The staging subdomain must be read, not guessed

`<workers-dev-subdomain>` is an **account-level** Cloudflare setting. It must be
read from the account before the exact callback is registered in Auth0. Auth0
matches the callback exactly, so a guessed subdomain produces an opaque redirect
failure at the first real login.

It has deliberately **not** been guessed or inferred anywhere in this repository.
Two ways to read it:

- **Dashboard** — Cloudflare → Workers & Pages → the account's `*.workers.dev`
  hostname appears in the Workers overview and in any Worker's subdomain URL.
- **API** — `GET /accounts/<account_id>/workers/subdomain` returns
  `{ "subdomain": "<value>" }`.

`wrangler whoami` reports the account **id** but not the subdomain, and Wrangler
exposes no command for it.

## Tenant and application checklist

1. **Read the account's `workers.dev` subdomain** from Cloudflare.
2. **Create the `release_approver` role.**
3. **Assign it only to authorised human approvers.** This is the control that
   makes an approval attributable to a person.
4. **Add a Post-Login Action** that copies assigned roles into the namespaced
   `https://villagestrongfoundation.org/roles` claim, **and explicitly add that
   claim to the ID token** (see below).
5. **Register the exact staging callback URL — no wildcards.**
6. **Keep RS256; do not enable HS256.**
7. **Do not create production callback URLs yet.**

### The step that silently breaks everything

Step 4 is where this usually goes wrong. A custom claim is **not included in the
ID token by default** — it lands in the access token, or nowhere at all. The
Post-Login Action must explicitly add the claim to the **ID token**.

If that toggle is missed, every approval fails with `ROLE_MISSING` while the
user is plainly logged in and visibly holds the role. Check the decoded ID token,
not the Auth0 dashboard.
## Why the algorithm setting is defence in depth

`PERMITTED_ALGS` in `src/oidc.ts` permits asymmetric algorithms only
(`RS*`, `ES*`). HS256 is never in that list, so an accidentally enabled HS256
would still be rejected at verification — a symmetric algorithm would let anyone
knowing the client secret mint an approval. Turning HS256 off in Auth0 is the
second layer, not the only one.

## Secrets

| Secret | Where |
|---|---|
| `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `OIDC_ROLE_CLAIM`, `OIDC_APPROVER_ROLES` | `wrangler secret put` |
| `OIDC_CLIENT_ID` | `wrangler secret put` |
| `OIDC_CLIENT_SECRET` | `wrangler secret put`, **staging Worker only** |
| `ORCHESTRATOR_API_TOKEN` | `wrangler secret put` |
| `ORCHESTRATOR_APPROVER` | `wrangler secret put`, **only** until OIDC is live |

Nothing above belongs in `wrangler.jsonc`, the lockfile, or a test fixture.
The client secret in particular must never be pasted into chat, a PR, or a
commit. The integration tests mint their own keypair, so CI needs no credentials.

## Values that must be generated, never invented

| Value | Determines |
|---|---|
| Auth0 tenant domain | `OIDC_ISSUER`, `OIDC_JWKS_URL` |
| Client ID | also `OIDC_AUDIENCE` |
| Client secret | staging Worker secret only |
| Account `workers.dev` subdomain | the exact callback URL |

## Deployment

The callback integration lands on an **isolated staging Worker**
(`village-strong-orchestrator-staging`), exposed on `workers.dev` only, and only
after explicit review. **Production deployment remains prohibited**: the
production Worker must not exist, the production zone and DNS stay untouched, and
the staging Worker keeps its own domains, data, identity, secrets, Durable Object
namespaces and admin interfaces, separate from `village-strong`.
