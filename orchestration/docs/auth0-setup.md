# Auth0 setup for release approvals

> **Status: design agreed, tenant not yet created.** No value below is real.
> `OIDC_CLIENT_SECRET` and the tenant domain must come from the Auth0 dashboard
> and must never be committed. Until the callback integration lands in a separate
> PR, none of this is wired into a live authorization flow.

Auth0 is the selected provider: standards-based Authorization Code + PKCE, a
per-user immutable `sub`, assignable roles, and RS256/JWKS signing that the
existing `jose` layer verifies without provider-specific code.

## Configuration

| Setting | Value |
|---|---|
| Application type | Regular Web Application |
| Flow | Authorization Code + PKCE |
| Signing algorithm | **RS256 only** |
| `OIDC_ISSUER` | `https://<tenant>.us.auth0.com/` |
| `OIDC_AUDIENCE` | The Auth0 application Client ID (validates the ID token `aud`) |
| `OIDC_JWKS_URL` | `https://<tenant>.us.auth0.com/.well-known/jwks.json` |
| `OIDC_ROLE_CLAIM` | `https://villagestrongfoundation.org/roles` |
| `OIDC_APPROVER_ROLES` | `release_approver` |
| `OIDC_CLIENT_ID` | Generated by Auth0 |
| Client authentication | Client secret, stored **only** as a Cloudflare secret |
| Staging callback | `https://orchestrator-staging.villagestrongfoundation.org/oidc/callback` |

The trailing slash on `OIDC_ISSUER` matters: `iss` is compared as an exact
string, so a missing or extra slash silently fails every token.

The role claim is a namespaced URI. `src/oidc.ts` reads it as a plain claim
lookup (`payload[roleClaim]`), so a namespaced claim needs no special handling —
and because the whole ID token is signature-verified first, a caller cannot
inject a role of their own.

## Tenant and application checklist

1. **Create the `release_approver` role.**
2. **Assign it only to authorised human approvers.** This is the control that
   makes an approval attributable to a person.
3. **Add a Post-Login Action** that copies assigned roles into the namespaced
   `https://villagestrongfoundation.org/roles` claim.
4. **Permit only the exact staging callback URL — no wildcards.**
5. **Keep RS256; do not enable HS256.**
6. **Do not create production callback URLs yet.**

### The one step that silently breaks everything

Step 3 is where this usually goes wrong. A custom claim is **not included in the
ID token by default** — it lands in the access token, or nowhere at all. The Post
-Login Action must explicitly add the claim to the **ID token**.

If that toggle is missed, every approval fails with `ROLE_MISSING` while the
user is plainly logged in and visibly holds the role. Check the decoded ID token,
not the dashboard.

## Why the algorithm setting is defence in depth

`PERMITTED_ALGS` in `src/oidc.ts` permits asymmetric algorithms only
(`RS*`, `ES*`). HS256 is never in that list, so an accidentally enabled HS256
would still be rejected at verification — a symmetric algorithm would let anyone
knowing the client secret mint an approval. Turning HS256 off in Auth0 is the
second layer, not the only one.

## Secrets

| Secret | Where |
|---|---|
| `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `OIDC_ROLE_CLAIM`, `OIDC_APPROVER_ROLES` | `wrangler secret put` |
| `OIDC_CLIENT_ID` | `wrangler secret put` |
| `OIDC_CLIENT_SECRET` | `wrangler secret put`, staging Worker only |
| `ORCHESTRATOR_API_TOKEN` | `wrangler secret put` |
| `ORCHESTRATOR_APPROVER` | `wrangler secret put`, **only** until OIDC is live |

Nothing above is a plain-text `var`. None of these values belong in
`wrangler.jsonc`, the lockfile, or a test fixture — the integration tests mint
their own keypair instead, so CI needs no credentials at all.

## Deployment

The callback integration must land on an **isolated staging Worker**, deployed
only for end-to-end testing. Production deployment remains prohibited, and the
staging Worker must stay separate from `village-strong` in domains, data,
identity, secrets, Durable Object namespaces and admin interfaces.

### Open question: the staging hostname

The proposed callback sits on `orchestrator-staging.villagestrongfoundation.org`,
which is a **subdomain of the zone that serves the production website**. That is
in tension with two constraints stated for this work:

- "Attach no production custom domain or public route", and
- "Keep it separate from `village-strong` domains".

The separation to date has been total — `village-strong-orchestrator` currently
has no hostname at all. Adding a hostname on the production zone is the first
step that touches shared DNS infrastructure, and a mistake there (wrong route,
wrong Worker binding, stray CNAME) is the kind that affects the live site rather
than just staging.

Options, in order of preference:

1. **A separate zone** (e.g. `villagestrong-staging.org`) owned for this purpose.
   Cleanest isolation; nothing shared with production.
2. **A private service binding** or tunnel, with no public hostname at all — the
   approver reaches it over a private path.
3. **A staging subdomain on the existing zone**, accepted knowingly, with the
   route configured to point only at the staging Worker.

This needs a decision before the callback PR, not during it.
